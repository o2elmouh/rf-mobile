## Risks & open questions

1. **The web's enriched `prolongation_candidates` shape ships as `{id, contract_number, end_date}` objects.** Older leads (pre-v1.14.1) stored bare UUIDs. Mobile's picker code must handle both — same defensive switch as the web's `LeadModal`:
   ```js
   const id = typeof c === 'string' ? c : c.id
   const label = typeof c === 'string' ? id : `${c.contract_number || id} — fin ${c.end_date}`
   ```
2. **Mobile fetches leads via `getLeads('pending')`** which proxies through the Express backend. Confirm the response shape includes `classification` and `prolongation_target_contract_id` (it should — `GET /leads` selects all columns). If it strips them, add the columns to the backend select.
3. **Backend `/contracts/:id/extend` vs web's direct supabase write.** Mobile uses the backend endpoint; web bypasses it. The backend endpoint computes `extraDays` and `extraAmount` itself and updates `return_date` + `total_amount`. **It does NOT create an invoice for the extra days** (the web does this on the client side via `saveInvoice`). Decision: leave as-is for v1.14.2; track "mobile prolongation invoicing" as a follow-up. The user can manually add an invoice from `InvoicesScreen` for now.
4. **No test coverage**, no regression safety net. Phases A–C are pure UI additions on stable screens, so risk is low, but verify visually on staging before pushing the version bump.
